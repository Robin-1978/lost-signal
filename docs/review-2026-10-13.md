# 外部方案评审结论

外部方案抓住了当前设计最缺少的一层：玩家应当关心一台逐渐恢复能力的机器人伙伴，而不只是完成一组工程实验。它提出的“为了推进冒险而理解机器人 AI”成为本轮修订的产品总原则。

## 直接采纳

- 采用有限规模研究基地和“失落信号”悬念，为任务提供持续动机。
- 将能力解锁表现为洛一行为发生变化，而不是普通数值升级。
- 使用“先体验现象、再改变因素、最后解释原理”的教学顺序。
- 保留感知、定位、计划和实际轨迹的内部状态可视化。
- P0 只验证一次“失败、理解、改造、再试、成功”的完整循环。
- 采用 C++20、raylib 和 TGUI 制作玩家版本，内容、仿真和表现保留清晰模块边界并编译为同一个程序。

## 调整后采纳

- “培养机器人”表达为恢复和理解真实能力，不加入好感度、喂养或纯数值养成。
- 第一章使用五个连续任务，但先单独制作最终组合任务作为纵向切片；验证失败后不扩展前置内容。
- 洛一可以有性格与短句，但技术表达必须由真实仿真状态触发。
- 算法对照和参数调试只进入后续高级实验室，不进入普通玩家主线。
- 知识提示会逐步减少结论提示，但感知、轨迹和事件证据始终可见。

## 不进入 MVP

- 视觉识别模型、机械臂、训练目标、强化学习和泛化章节。
- 自由几何机器人搭建、多底盘和多机器人协作。
- 社区关卡、排行榜、每日挑战、ROS 2 与真实硬件连接。
- 让玩家在主线中直接选择 A*、DWA 或调整工程参数。

## 对外部方案的不足判断

外部方案的产品主题和剧情动机成立，但还不是可直接生产的设计。它没有定义具体 UI 层级、回放数据契约、内容 Schema、存档迁移、确定性验证和每关的多解约束；“中期选算法、后期做训练”也会让个人项目过早承担两套玩家复杂度。

最初建议使用带账号授权流程的商业引擎，实际安装和分发成本会干扰原型验证，因此该判断被后续实现推翻。发行版采用 C++20、zlib 许可的 raylib/TGUI 与 JSON 数据：无需账号和激活，算法、任务逻辑和玩家客户端共享一套类型与构建链，适合开源协作和后续跨平台发布。

## 最终产品判断

产品核心不再定义为“机器人教育控制台”，而是：

> 玩家在一场基地冒险中唤醒洛一，通过观察真实失败和恢复自主能力，让它逐渐学会独立面对世界。

剧情负责让玩家想继续，真实仿真负责让失败可信，因果回放负责把技术变成可以推理的谜题。三者缺少任何一个，产品都会分别退化成教学软件、普通冒险或不可解释的黑盒演示。
